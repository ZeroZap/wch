# WCH MCU 基址与寄存器定义对比报告

## 1. 范围与方法

本报告集中分析 `ch32_header` 中现有的 16 份 MCU 头文件，它们是本次对比采用的集中快照。报告不是对仓库内所有 EVT 版本头文件的穷举，也不替代芯片数据手册。

本轮另对若干 EVT 目录中的头文件副本做了抽查。抽查结果显示主要外设基址与 `ch32_header` 集中快照总体一致，但这只能作为局部交叉检查，不能证明所有 EVT 发布版本、芯片修订和条件编译组合都一致；下文表格和统计仍仅以 `ch32_header` 集中快照为口径。

| 类别 | 头文件 | 数量 |
|---|---|---:|
| CH32/CMSIS 风格 | `ch32v10x.h`、`ch32v20x.h`、`ch32v30x.h`、`ch32v4x7.h`、`ch32x035.h`、`ch32x3x5.h`、`ch32m030.h`、`ch32l103.h`、`ch32h417.h` | 9 |
| CH5XX/SFR 风格 | `CH56xSFR.h`、`CH572SFR.h`、`CH573SFR.h`、`CH583SFR.h`、`CH585SFR.h`、`CH592SFR.h`、`CH595SFR.h` | 7 |

对比包含三层：

1. 地址空间和总线根基址。
2. 外设实例最终绝对地址。
3. 同名外设的寄存器布局、成员宽度和访问模型。

需要特别区分两个概念：

- **基址兼容**：外设块从相同地址开始。
- **寄存器兼容**：块内偏移、宽度、语义和访问属性都一致。

基址相同不代表寄存器兼容。例如 CH592 与 CH595 的 Flash 块都从 `0x40001800` 开始，但 `FLASH_DATA` 分别位于 `0x40001800` 和 `0x40001810`。

## 2. 总体结论

1. `CH32` 与 `CH5XX` 不只是基址不同，而是**寄存器描述模型和 SoC 地址规划均不同**。
2. `CH32` 传统低速外设大多沿用 STM32F1 风格地址：`TIM2=0x40000000`、`GPIOA=0x40010800`、`RCC=0x40021000`。跨 CH32 子系列时，这部分地址高度稳定。
3. `CH5XX` 把整个 SFR 窗口集中在 `0x40000000-0x4000FFFF`，常见块为 SYS `0x40001000`、Timer `0x40002000` 起、UART `0x40003000` 起、SPI `0x40004000` 起、PWM `0x40005000`、USB `0x40008000`。
4. `CH32` 主要使用 `TypeDef` 结构体和实例指针；`CH5XX` 主要使用 `R8_`、`R16_`、`R32_` 绝对地址左值宏。同一 CH5XX 地址经常有多个访问宽度和语义别名。
5. CH32 内部不能把所有同名 `*_TypeDef` 视为同一 IP。差异最大的公共类型包括 `ADC`、`TIM`、`RCC`、`AFIO`、`USB`、`DMA_Channel`、`GPIO` 和 `USART`。
6. CH5XX 可再分为 CH573/583 传统族、CH592/595 新 CH59 族、CH585 高端 CH58 族、CH572 紧凑族、CH56x 高吞吐独立族。
7. 统一库应把“实例地址”“寄存器布局/IP 版本”“芯片能力”拆为三份元数据，不能以芯片系列宏直接包住一套超大通用结构体。

## 3. 两种定义模型

### 3.1 CH32：结构体加实例基址

典型形式：

```c
typedef struct {
    __IO uint32_t CTLR;
    __IO uint32_t CFGR0;
    /* ... */
} RCC_TypeDef;

#define RCC_BASE (AHBPERIPH_BASE + 0x1000)
#define RCC      ((RCC_TypeDef *)RCC_BASE)
```

特征：

- 结构体成员顺序表达寄存器偏移。
- `__I`、`__O`、`__IO` 表达基本访问属性。
- 一个结构体可供多个实例复用。
- 匿名联合用于 16/32 位寄存器视图或别名。
- 必须校验 `offsetof`，因为同名结构体在不同头文件中可能不是同一布局。

### 3.2 CH5XX：绝对地址加访问宽度宏

典型形式：

```c
#define R32_TMR1_CONTROL (*((PUINT32V)0x40002400))
#define R8_TMR1_CTRL_MOD (*((PUINT8V) 0x40002400))
#define R8_TMR1_CTRL_DMA (*((PUINT8V) 0x40002401))
#define BA_TMR1          ((PUINT8V)  0x40002400)
```

特征：

- `R8_`、`R16_`、`R32_` 名称表示期望访问宽度。
- 同一个物理地址可能同时有 8/16/32 位视图。
- `BA_*` 加裸偏移宏提供第二套访问方式。
- `RO`、`WO`、`RW1`、`RWA` 等属性通常只存在于注释，C 类型不会阻止错误访问。
- CH56x 的 USBSS、SERDES 等复杂块局部使用结构体，但常规外设仍是绝对地址宏，属于混合模型。

按头文件中行首宏粗略统计，CH5XX 的寄存器视图数量如下。一个物理寄存器可能被重复计数，因此该表表示头文件 API 复杂度，不表示唯一寄存器数量。

| 文件 | `R8_` | `R16_` | `R32_` |
|---|---:|---:|---:|
| CH56x | 231 | 50 | 150 |
| CH572 | 128 | 50 | 62 |
| CH573 | 199 | 47 | 99 |
| CH583 | 252 | 69 | 117 |
| CH585 | 269 | 83 | 166 |
| CH592 | 208 | 66 | 111 |
| CH595 | 232 | 75 | 139 |

## 4. CH32 地址对比

### 4.1 根地址和总线命名

| 文件组 | Flash | SRAM | Peripheral | 子总线表达 |
|---|---:|---:|---:|---|
| V10/V20/V30/X035 | `0x08000000` | `0x20000000` | `0x40000000` | APB1 `+0x00000`、APB2 `+0x10000`、AHB `+0x20000` |
| L103/M030 | `0x08000000` | `0x20000000` | `0x40000000` | PB1 `+0x00000`、PB2 `+0x10000`、HB `+0x20000` |
| X3X5/V4X7 | `0x08000000` | `0x20000000` | `0x40000000` | 单一 HB 根，直接使用完整偏移 |
| H417 | `0x08000000` | `0x20100000` | `0x40000000` | 单一 HB 根；另有 ITCM `0x200A0000`、DTCM `0x200C0000` |

总线宏名称不同，但很多最终地址相同。例如旧式 `AHBPERIPH_BASE + 0x1000` 和新式 `HBPERIPH_BASE + 0x21000` 最终都得到 RCC `0x40021000`。

### 4.3 差异集中区

| 功能 | X035 | M030 | L103 | X3X5 | V20/V30 | V4X7 | H417 |

USB 是地址复用最明显的区域：

- `0x40023400` 在 X035/M030/H417 是 USBFS，在 V30/V4X7 是 USBHS，在 X3X5 是 ARGB。
- `0x40024400` 在 X3X5/H417 是 USBPD，在 V4X7 是 PSRAM。
- `0x40038000` 在 X3X5 是 USBSS，在 H417 是 UHSIF。
- V20/V30/L103 的 USBFS 被独立映射到 `0x50000000`。

因此统一库中禁止用固定地址识别外设种类，应由芯片元数据提供实例类型和基址。

### 4.4 CH32 资源差异摘要

| 芯片头 | 主要资源特征 |

| M030 | 双 USBPD、USBFS、扩展模拟/电流 sink；无 IWDG；Option Byte 地址特殊 |

| H417 | TCM、DMAMUX、CAN3、I3C、LTDC、SAI、DFSDM、HSADC、QSPI、SDMMC、FMC、USB FS/HS/SS、SerDes |

## 5. CH32 同名寄存器布局差异

### 5.1 可作为稳定基线的类型

以下结构在定义它们的头文件中基本一致：

| 类型 | 公共字段 |
|---|---|
| `DMA_TypeDef` | `INTFR, INTFCR` |
| `EXTI_TypeDef` | `INTENR, EVENR, RTENR, FTENR, SWIEVR, INTFR` |
| `IWDG_TypeDef` | `CTLR, PSCR, RLDR, STATR` |
| `WWDG_TypeDef` | `CTLR, CFGR, STATR` |
| `OB_TypeDef` | `RDPR, USER, Data0, Data1, WRPR0..3` |

即使这些类型稳定，实例数量和时钟/复位控制位仍是芯片能力差异。

### 5.2 DMA 通道

| 布局 | 文件 | 字段 |
|---|---|---|
| DMA channel v1 | V10/V20/V30/V4X7/X035/M030/L103 | `CFGR, CNTR, PADDR, MADDR` |
| DMA channel v2 | X3X5/H417 | 上述字段加 `M1ADDR` |

地址步距也不统一：

- 传统通道多为 `0x14`：Ch1 `+0x08`、Ch2 `+0x1C`。
- V4X7 的 Ch8 以后以及 V30 DMA2 Ch8 以后使用 `0x10` 步距。
- X3X5 的 11 通道仍使用 `0x14` 步距。

结论：不可用 `base + 0x08 + channel * stride` 的单一公式覆盖全部芯片，应存储每通道基址或为每个 DMA IP 版本定义地址算法。

### 5.3 ADC

所有 CH32 ADC 有传统序列/注入序列公共前缀，但尾部扩展完全不同：

| 文件组 | 公共布局后的扩展 |
|---|---|
| V10/V20 | 无 |
| V30/V4X7 | `AUX` |
| H417 | `AUX, DRV` |
| L103 | `CFG` |
| X035 | `CTLR3, WDTR1..3` |
| X3X5 | `SMPMD, UDP, CONCFG, SCANCNT` |
| M030 | `CTLR3, WDTR1, WDTR2, AVGTR, DLYR, AVGDR, RDATAR2..4` |

ADC 应至少拆成传统 ADC、增强 ADC、X035 ADC、X3X5 ADC、M030 ADC、L103 ADC、H417 ADC 等布局版本。

### 5.4 GPIO 与 AFIO

GPIO 公共前缀为 `CFGLR, CFGHR, INDR, OUTDR, BSHR, BCR, LCKR`。

| 文件组 | GPIO 尾部 |
|---|---|
| V10/V20/V30/V4X7/L103/M030 | 无 |
| X3X5/H417 | `SPEED` |
| X035 | `CFGXR, BSXR` |

AFIO 的差异更大：传统芯片使用 `ECR/PCFR1/EXTICR/PCFR2`；X3X5 和 H417 加入每端口 `AFLR/AFHR`；X035/M030 是裁剪布局。建议 GPIO 数据寄存器操作与引脚复用配置分成两个 IP trait。

### 5.5 RCC

RCC 同名但布局随系列明显变化：

| 文件组 | 关键特点 |
|---|---|
| V10 | 传统 10 寄存器布局 |
| V20/V30 | 增加 `AHBRSTR, CFGR2` |
| L103 | PB/HB 命名，含 `HBRSTR` |
| M030 | 无 `BDCTLR`，末尾 `HBPRSTR` |
| X035 | `INTR` 和 `BDCTLR` 槽位保留 |
| X3X5 | HB1/HB2 命名，无 `BDCTLR` |
| V4X7 | HB/PB 命名，增加 `CFGR3` |
| H417 | 增加 `PLLCFGR`、`PLLCFGR2`，寄存器顺序变化 |

时钟驱动必须按 RCC 布局独立实现，不能用单一结构体加可选字段尾部解决，因为 H417 在前部插入了 `PLLCFGR`。

### 5.6 TIM

TIM 是公共外设中布局别名最多的一类：

| 文件组 | 主要差异 |
|---|---|
| V10 | 传统 16 位寄存器加 16 位保留槽 |
| V20 | CNT/ATRLR/CHxCVR 提供 32 位联合视图 |
| V30/V4X7 | 传统布局，尾部增加 `AUX` |
| H417 | 32 位联合视图，尾部 `AUX` |
| L103/X3X5 | 以 `*_TIM4` 呿名 32 位视图 |
| X035 | `*_R32` 视图，尾部 `SPEC`，部分字段名有双下划线 |
| M030 | CH1..4 为 32 位，并扩展 `AUX1/AUX2/CH5..8` |

统一接口可以抽象计数、比较、PWM 能力，但寄存器访问层应至少按上述布局分组。

### 5.7 USART、SPI、I2C

- USART 基础布局在 V10/V20/X035/M030/L103 接近；V30/V4X7/H417 增加 `CTLR4`；X3X5 的 32 位 `BRR` 使中段布局改变。
- SPI 在 V20/V30/V4X7/H417 包含 I2S 配置槽；V10/L103/M030/X035 以保留字段占位；X3X5 的保留数组命名不同。
- I2C 传统版本带 `RTR`，X035/X3X5/M030 不带。即使公共前缀可复用，也需要布局尺寸和能力标记。

### 5.8 USB 和 USBPD

USBFS、USBHS、USBSS 必须视为不同 IP。即使同为 USBFS，X035 的端点布局、传统 `0x50000000` USBFS 布局、H417/M030 的布局也不能默认相同。

USBPD 的 5 个 32 位槽总体接近，但别名不同：

- X3X5/H417 的 DMA 槽只暴露 `USBPD_DMA`。
- L103/X035 还暴露 16 位 `DMA` 视图。
- M030 的 CC1/CC2 槽按字节拆开，并有两个 USBPD 实例。

### 6.2 SYS 和 GPIO 是主要族群分界

CH56x：

- `SAFE_ACCESS` 从 `0x40001000` 开始。
- GPIOA/B 位于 `0x40001040/0x40001060`。
- GPIO 每端口有独立 `DIR/PIN/OUT/CLR/PU/PD/DRV/SMT`。

CH572/573/583/585/592/595：

- 多数 `SAFE_ACCESS` 位于 `0x40001040`。
- GPIO 中断控制位于 `0x40001090` 附近。
- GPIOA/B 通常位于 `0x400010A0/0x400010C0`。
- 传统端口布局多为 `DIR/PIN/OUT/CLR/PU/PD_DRV`，较新芯片增加 `SET`。

所以 CH56x GPIO/SYS 必须是独立实现；其 Timer/UART/SPI 只能在验证偏移后局部复用。

### 6.3 CH5XX 子族差异

#### CH573 与 CH583

CH573 是传统基础布局；CH583 在保留 SYS、GPIO、Timer、UART、PWM 地址的基础上增加 SPI1、I2C、USB2 和低功耗/模拟功能。二者适合共享基础 IP 驱动，但能力表不同。

#### CH583 与 CH585

CH585 延续 CH583 的基础地址，同时增加 IWDG、624 MHz PLL、ADC scan、GPIO SET、LCD、USBHS、NFC 和 LED。普通 Timer/UART/SPI/I2C 可较高程度复用；clock/power/ADC/USB 必须分版本。

#### CH592 与 CH595

二者外围骨架最接近，但存在关键不兼容：

| 功能 | CH592 | CH595 |
|---|---|---|
| Flash 数据寄存器 | `FLASH_DATA=0x40001800` | `FLASH_DATA=0x40001810` |
| `0x1014-0x1017` | `SLEEP_CTRL3` | long reset、clock off2、wake config |
| SPI `+0x08/+0x09` | `CTRL_MOD1/CTRL_MOD2` | `STATUS1/INT_TYPE`，另有扩展中断 |
| TouchKey | 传统 count/convert/config | `TKEY_CFG2`、传输周期、通道使能 |
| 新外设 | LCD | LCD、KEYSCAN、ENC、LED |

这说明“同一 CH59 家族”也不能等同为寄存器兼容。

#### CH572

CH572 是紧凑重排版本：单 GPIOA、单 Timer、单 UART、单 SPI，带 I2C、KEYSCAN、Encoder 和 comparator。KEYSCAN 位于 `0x40001064`，Encoder 位于 `0x40002420`；CH595 中对应功能已迁到 `0x40006040/0x40006080`。

#### CH56x

CH56x 是独立高吞吐族，包含 HSPI、ECDC、USBSS、USBHS、eMMC、SERDES、Ethernet、DVP 和外部总线。它与低功耗无线族只共享部分 Timer/UART/SPI IP 风格，不应共享 SoC 级寄存器地图。

### 6.4 同地址多宽度视图

CH5XX 中经常出现：

```text
0x40002400 -> R32_TMR1_CONTROL
0x40002400 -> R8_TMR1_CTRL_MOD
0x40002401 -> R8_TMR1_CTRL_DMA
```

统一结构体若只定义一个 `uint32_t CONTROL`，会丢失硬件要求的字节访问接口；若只定义字节成员，又会丢失原子 32 位视图。可采用显式 union，但必须注意：

- 不同宽度访问可能具有不同副作用。
- RO/WO/RW1/RWA 等属性不能只靠普通 `volatile` 表达。
- 宏名前缀不能完全保证实际指针宽度，当前头文件中存在命名与指针类型不一致项。

## 7. 头文件中发现的异常与风险

以下项目应在自动提取时报告，不能静默归一化：

| 文件 | 问题 |
|---|---|
| `ch32h417.h` | `UHSIF` 实例使用 `UHSIF_TypeDef`，但本文件未找到该类型定义 |
| `ch32v20x.h` | `ETH10M_TypeDef` 受条件编译保护，但 `ETH10M` 实例宏未使用同样条件 |
| `CH572SFR.h` | 地址图的 CODE 范围约 240 KiB，但 `SZ_CODE` 为 512 KiB |
| `CH573SFR.h` | 地址图 CODE 范围为 512 KiB，但 `SZ_CODE` 为 256 KiB |
| `CH592SFR.h` | 地址图 RAM 为 32 KiB，而 `SZ_RAM=0x6800`，可能是物理窗口与用户可用量口径不同 |
| `CH572SFR.h` | 地址图声明 LCD `0x40006000` 块，但主 SFR 区未找到对应 LCD 寄存器宏 |
| `CH573SFR.h`、`CH583SFR.h` | `R16_AUX_POWER_ADJ` 名称为 16 位，右侧却使用 8 位指针 |
| `CH573SFR.h`、`CH583SFR.h`、`CH592SFR.h` | `R8_PWM_INT_CTRL` 名称为 8 位，右侧却使用 32 位指针 |

另外：

- M030 的 Option Byte 为 `0x1FFFF300`，其他多数 CH32 为 `0x1FFFF800`。
- H417 的 SRAM 为 `0x20100000`，并另有 ITCM/DTCM，不能沿用其他 CH32 的 `0x20000000` SRAM 假设。
- V30 的 USBHS device/host 指针使用同一 base；V4X7/X3X5/H417 的 host 通常为 device base `+0x100`。

## 8. 对统一库设计的建议

### 8.1 建议的数据模型

不要按“每个 MCU 一套手写 HAL”或“所有 MCU 一个最大结构体”二选一。建议拆成三层：

```text
Chip capabilities
  - 实例数量、通道数量、引脚和可选功能

Peripheral instances
  - 实例名、绝对基址、IRQ、DMA request、clock/reset gate

Register layout/IP version
  - 字段偏移、宽度、访问属性、别名和特殊语义
```

示意：

```rust
struct PeripheralInstance {
    kind: PeripheralKind,
    layout: LayoutId,
    base: usize,
    clock: ClockGate,
    reset: Option<ResetGate>,
}
```

`TIM2@0x40000000` 在多个 CH32 上基址相同，但其 `layout` 可以分别是 `TimV1`、`Tim32Alias`、`TimAux` 或 `TimM030`。

### 8.2 推荐的初始 IP 分组

| 外设 | 推荐起始分组 |
|---|---|
| CH32 GPIO data | 传统、SPEED、X035 扩展三组 |
| CH32 AFIO | 传统、L103、X035、M030、X3X5、H417 |
| CH32 DMA channel | 4-word、5-word，再按后段地址步距分组 |
| CH32 ADC | V10/20、V30/4X7、H417、L103、X035、X3X5、M030 |
| CH32 TIM | V10、V20、V30/4X7、H417、L103/X3X5、X035、M030 |
| CH32 RCC | V10、V20/30、L103、M030、X035、X3X5、V4X7、H417 |
| CH32 USB | FS legacy、FS compact、HS old、HS split、SS，各自再验证版本 |
| CH5XX SYS/GPIO | CH56x、CH572、CH573/583、CH585、CH592、CH595 |
| CH5XX Timer/UART/SPI | 先按偏移签名聚类，再用差异寄存器拆版本 |
| CH5XX Flash | CH57/58/592 legacy、CH595 new、CH56x SPI ROM |

### 8.3 自动提取器要求

建议后续提取工具同时输出 JSON/CSV 和 Markdown，并保留原始证据：

1. CH32 解析 `#define *_BASE` 表达式，求值为绝对地址。
2. CH32 解析 `typedef struct`，输出成员名、`offsetof`、宽度、数组长度和访问限定。
3. CH5XX 解析每个 `R8/R16/R32` 宏右侧的实际指针类型和绝对地址，不能仅相信宏名前缀。
4. 按绝对地址聚合同地址别名，保留所有访问宽度。
5. 解析注释中的 `RO/WO/RW/RW1/RWA` 等属性。
6. 同时解析 `BA_*` 与 offset，并检查其计算结果是否与绝对地址宏一致。
7. 为每个外设生成寄存器布局签名，例如 `(offset,width,access)` 序列的 hash，用签名而不是名称判断兼容。
8. 对重叠、未定义类型、条件编译不对称、宏名宽度与实际类型不一致发出诊断。

### 8.4 编译期校验

生成 CH32 结构体后，应为每个布局加入：

```c
_Static_assert(offsetof(GPIO_TypeDef, OUTDR) == 0x0C, "GPIO OUTDR offset");
_Static_assert(sizeof(DMA_Channel_TypeDef) == expected_size, "DMA layout");
```

对于 CH5XX，建议生成地址和宽度校验表，而不是强制把所有寄存器转成结构体。对有副作用或必须窄访问的寄存器保留专用 accessor：

```rust
unsafe fn write8(addr: usize, value: u8);
unsafe fn write16(addr: usize, value: u16);
unsafe fn write32(addr: usize, value: u32);
```

### 8.5 实施优先级

1. 先统一 CH32 的稳定公共块：EXTI、IWDG、WWDG、DMA 控制器头和传统 GPIO 数据操作。
2. 再按布局版本接入 TIM、USART、SPI、I2C。
3. ADC、RCC、AFIO、Flash、USB 和模拟模块保持子族专用，待布局签名稳定后再抽象。
4. CH5XX 先建立地址/宽度/accessor 元数据，不急于转换为 CMSIS 大结构体。
5. 最后统一高层能力接口，例如 GPIO、串口、定时器和 SPI trait；底层寄存器块仍保持 IP 版本隔离。

## 9. 最终判断

当前初步判断“主要是 CH5XX 与 CH32 基址不同”是正确的第一层结论，但还不足以指导统一库：

- CH32 的传统外设地址非常稳定，差异主要在资源数量和结构体尾部/别名扩展；RCC、ADC、TIM、AFIO、USB 等存在实质布局变化。
- CH5XX 的外围地址骨架在多数无线芯片间也很稳定，但 SYS、Flash、clock/power、ADC/TouchKey 及 USB 演进明显；CH56x 基本应视为独立 SoC 族。
- 真正可复用的单位不是“CH32 系列”或“CH5XX 系列”，而是**具有相同寄存器布局签名的外设 IP 版本**。

统一库最安全的主键应为：

```text
(chip, peripheral instance) -> (absolute base, layout ID, capabilities)
```

而不是：

```text
peripheral name -> fixed base + one universal register struct
```

## 11. 证据边界

- 本报告的完整对比集合仅为 `ch32_header` 集中快照中的 16 份头文件。
- EVT 副本抽查主要用于发现集中快照与示例工程是否存在明显基址冲突；目前抽查的主要基址总体一致，但没有逐版本、逐宏和逐寄存器布局完成证明。
- 因此“地址稳定”“布局一致”均只描述本报告样本；生成统一库前仍应锁定具体 EVT/SDK 版本，并对实际使用的头文件执行自动地址求值、`offsetof` 和编译期校验。
